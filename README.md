# 科学计算工作区的 Agent 规约

一套面向**长周期、可审计、多设备**分子动力学（GROMACS）任务的 AI agent 行为规约。

本仓库**只包含规约层**：边界定义、方法依据、能力封装。不含数据、不含工具链实现、不含第三方材料。

---

## 这个仓库是什么

一套在实践中逐步长出来的 agent 工程规约，回答一个具体问题：

> 当 AI agent 要替人跑几天到几周的数值计算、操作远程集群、产出可能进入论文的结果时，
> 什么样的约束能让它的输出**可审计、可复算、可信**？

规约分三层，职责不重叠：

| 层 | 位置 | 作用 |
|---|---|---|
| **边界** | `AGENTS.md` | 不可违反的硬约束。长期稳定，改动需慎重 |
| **依据** | `docs/` | 每条边界的方法学理由、枚举定义、操作细节 |
| **能力** | `.agents/skills/` | 具体平台的封装能力，含校验脚本与模板 |

**本仓库只分发前两层。** 能力层依赖平台的授权材料、且高度绑定平台版本，由各工作区自行维护，不含在本仓库内。

`CLAUDE.md` 是 Claude Code 的入口垫片，指向 `AGENTS.md`。

## 这个仓库不是什么

| 不含 | 原因 |
|---|---|
| 轨迹、拓扑、任务输入与结果 | 数据驻留原则：本地长期区不保留轨迹 |
| GROMACS 分析脚本与 Python 依赖 | 属工具链层，单独维护 |
| 力场文件 | 第三方版权，不再分发 |
| 平台厂商手册 | 第三方版权，需自行获取 |
| 服务器地址、SSH 别名、凭据 | 凭据分离原则，见下 |

## 设计原则

每条原则都对应一个真实踩过的失效模式，不是纸面规范。

| 原则 | 防的是什么 |
|---|---|
| **四层状态**：执行 / 产物 / 验收 / 发布，分别记录，不互相推导 | 用"跑完了"掩盖"结果没验证过"。退出码为 0 不等于科学上成立 |
| **Attempt 不可覆盖**：重跑、续跑、改参数都建新 attempt，只增不复用 | 失败证据被覆盖，事后无法判断哪一版进了结论 |
| **Pilot 门禁**：新体系 / 新版本 / 新链路先跑最小代表性样例 | 用三天的生产任务去发现一个五分钟就能暴露的输入错误 |
| **数据驻留**：本地长期区不留轨迹，临时分析只进指定临时根 | 同步盘被 TB 级轨迹撑爆；临时目录变成唯一数据来源 |
| **标识分离**：`server_id` / `deployment_profile` / `local_alias` 三者分离 | 把设备专属连接信息写进通用文档；跨设备静默沿用旧配置 |
| **Replay 与 Manifest**：命令、参数、种子、输入哈希、依赖 attempt 全部记录 | 半年后无法回答"这张图是哪一次跑的" |
| **不把"看起来对"当验收**：性能好、图形正常、最低瞬时能量低，都不是放行依据 | 视觉上合理的轨迹掩盖采样未收敛或参数错误 |

## 配置模板

两个模板描述规约要求的**标识分离**如何落地：

- `config/gromacs-deployments.toml.example` — 跨设备共享的**非秘密**执行元数据（profile、远程根、激活方式）
- `config/gromacs-local.toml.example` — 每台设备各自的 route / alias 选择与临时目录根

两者都**只保存非秘密字段**。真实 local config 不进版本库，且不保存密码、私钥或 token。

## 能力层为何不在本仓库

第三层是平台专属能力（skill）：把某个计算平台的手册要求与实证经验固化成可执行步骤、校验脚本与模板。

它不在本仓库分发，原因有二：依赖平台的授权手册，且高度绑定平台版本。使用本规约时，应在自己的工作区里维护对应的 `.agents/skills/<skill>/`。

规约对能力层本身的要求是：**平台专属的输入准备与校验必须走独立 skill**，不得散落在临时脚本或对话上下文里，以便复用、版本化与审计。`AGENTS.md` §13 给出了这条路由规则。

## 适用范围与已知边界

**这套规约是在一个真实私有工作区里长出来的，但它描述的是目标态。** 那个工作区里仍存在形成于规约之前的早期数据布局；本规约不对历史事实做追溯性改写，迁移需单独审计。使用时应把它当作**前向约束**：对已有数据保持记录不动，对新增工作按规约执行。

**版本相关的内容会过时。** GROMACS 版本、力场目录名、平台手册版本、输出文件命名规则都写在文档里并标注了来源版本。升级后需要重新验证，不能沿用旧版本的解析与性能假设。未经验证的结论按 A/B/C/TODO 标记成熟度，记录在工作区本地的成熟度与待办文档中（不在本仓库分发）。

**这是一套有主张的规约，不是通用框架。** 它假设了长周期计算、远程执行、结果可能进入正式交付。轻量的一次性计算任务套用它会明显过重。

## 如何应用到你自己的工作区

1. 读 `AGENTS.md`，把不适用的条款删掉
2. 按 `docs/task-layout-and-replay.md` 建立任务逻辑根与 attempt 编号
3. 按 `docs/deployment-and-device-resolution.md` 落地 profile / alias 分离，从 `config/*.example` 起步
4. 新体系先跑 pilot，通过后再扩大规模

> **一条实践建议**：这套规约最大的风险不是不够严格，而是**写了却做不到**。
> 规约一旦存在，就会被当作已生效的事实引用。删掉执行不了的条款，比留着它们更好。
