# 完整性与归档策略

## 1. 目标

manifest 描述“有什么、来自哪里、服务什么”；SHA-256 描述“当前字节是否与记录一致”。两者都不能省略。哈希清单本身也应有版本、生成时间和范围说明。

## 2. Manifest 最小字段

正式任务至少维护一个任务或 attempt manifest，建议字段：

```text
task_id, attempt_id, stage, artifact_id, role, path, source,
size_bytes, sha256, version, created_at, state, notes
```

批量任务增加成员 ID、输入 ID、远程前缀、时间范围和父 artifact。文件改名不能丢失 `artifact_id` 和来源关系。

## 3. 哈希范围

必须对冻结输入、mdp/拓扑、实际运行日志、TPR/CPT、最终结构、分析结果、manifest 和交付包生成 SHA-256。远程轨迹可逐文件哈希，也可对已验证归档哈希并附成员清单；必须明确使用哪一种。

哈希命令、算法、路径基准和换行策略写入 README。Windows 与 Linux 传输后，以文件字节为准复核；不要只比较文件名、大小或压缩包哈希。

## 4. 上传与下载

上传前生成输入清单，上传后在远端复核；下载后在本地临时分析根逐文件复核。发现不一致时将 artifact 标记为 `MISMATCH`/`PARTIAL`，保留证据并停止后续科学分析。

远程压缩归档只用于传输或短期 staging。解包后逐成员校验，确认目录结构、数量和哈希，再把解包内容作为唯一正式副本。不要把压缩包和解包内容都作为长期权威副本。

## 5. 归档层级

- `working`：当前 attempt 正在使用的远程文件；
- `verified`：通过数量、结构、哈希和状态门禁的结果；
- `released`：已批准交付的文件与清单；
- `retired`：仍保留但不再作为默认输入的旧 attempt。

层级变化必须在 manifest 和任务 README 中记录。retired 不等于可删除。

## 6. 交付包

交付目录应有明确白名单，包含 manifest、报告和 `SHA256SUMS`。交付前检查：

1. 无白名单外文件；
2. 每个文件可追溯到 task/attempt/analysis；
3. 哈希清单可独立验证；
4. 状态为 `RELEASED` 或明确标注候选/限制；
5. 不把未验收结构命名为 final。

## 7. 清理策略

清理必须先盘点、再验证独立副本或重建来源、最后执行。当前规约请求未授权删除时，不做清理。

删除传输临时包属于可选运维动作，需记录路径、范围、验证结果和时间。不得删除失败 attempt、原始日志或唯一远程轨迹。

## 8. 复核命令

通用复核思路是从清单所在目录执行 SHA-256 校验，并比较文件计数与目录角色。具体命令按平台和现有工具选择；不能假定 Windows shell、GNU 工具或远程版本始终一致。
